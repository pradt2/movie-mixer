# TASK_09 — Protect source media and enforce asset identity

Prerequisite: TASK_08. Read AGENTS.md. This is a corrective milestone, not a new editing feature.

## Review findings (baseline 0c6b8f1)
- **Critical data-loss risk:** `render/exporter.py:RenderRequest.resolve_tools` permits destination == an imported media path if overwrite is true. `render()` eventually calls `staging.replace(request.destination)`. The overwrite confirmation in `ui/main_window.py:_export_composition` even promises that imported assets are never modified. Save As likewise allows an arbitrary existing filename and `project/storage.py:save_document` replaces it. Ordinary confirmation must NOT authorise destroying source media.
- **Incorrect-source risk:** `project/storage.py:_check_identity` detects changed files on load, but `ui/main_window.py:_missing_asset_names` accepts any existing regular file and `RenderRequest.resolve_tools` checks only existence. A different encode at the same path can therefore be used with obsolete stream bounds, indexes and timestamps. Check identity again during an editing session, not only at load.
- **Race:** existence/overwrite validation happens before the potentially lengthy render; unconditional replace can overwrite a file created in the meantime. Cancellation after the last progress event can still publish a file.

## Implement
1. Establish one reusable destination protection helper outside Qt. Check all imported assets, including unplaced/muted assets and other protected project paths, not just streams participating in the current render. Use normalized resolved paths and same-file device/inode comparison for existing paths (symlink, hardlink and relative aliases). Reject source collisions unconditionally even with overwrite consent. Use the same checks in project saves, export/preview backend, and UI preflight; error messages identify the conflicting file.
2. Keep the original atomic staging scheme. For overwrite=False, publish atomically without clobber (e.g. same-filesystem hard-link publication with EEXIST handling on Linux; clean up the staging name). For authorised replacement revalidate protection and destination identity immediately before publication; refuse if the file the user approved has been replaced/changed since consent. Never delete the previous output before a successful publish. Check cancellation before publishing. Document the residual limitations of filesystem races rather than claiming absolute guarantees on unsupported filesystems.
3. Introduce a read-only media identity/availability check with explicit ONLINE/MISSING/CHANGED/UNREADABLE results. Pass recorded identities to render/decode requests; validate once per asset at operation boundary, and validate again before publishing render if source identity changed during the job. Reuse the project storage identity policy (size + mtime_ns, not a claim of cryptographic identity). Distinguish a changed asset from missing; require explicit validated relink/reimport. Do not silently accept new metadata. UI should use this policy rather than merely is_file(). Do not stat every clip on every paint.
4. Validate protection and identity also for source preview, stills, thumbnails/waveforms and relinking. Invalid media should produce an actionable status, not a misleading cached image or silently substituted soundtrack. If a range does not use an unavailable asset, allow rendering that range when it can be determined safely (do not relax source protection for unused assets).

## Acceptance
- Tests with synthetic files: export and Save As to an imported asset, including unused asset, relative alias, symlink and hardlink, with overwrite=True. Refuse and prove original bytes/hash unchanged; no debris.
- Simulate a destination created between preflight and publication, a replacement after overwrite confirmation, and cancellation just before publish; previous/user-created file remains byte-identical.
- Change a source at the same path both after import and after reopen; still/preview/export must refuse stale metadata and explicitly report CHANGED. After successful validated relink the correct file can be used.
- Existing-output protection and atomic save/recovery tests still pass. No real user media in tests. Update architecture and progress.
